# L1-02 · Storage

The instinct most people bring to storage is that it's a capacity problem. You have some bytes, you need somewhere to put them, and the only real question is how many bytes and how much it costs to keep them. That instinct is why storage decisions age badly. The amount of data almost never determines which storage system you should reach for; how that data is read and written does. A hundred gigabytes of video and a hundred gigabytes of transaction records are the same size and almost nothing else in common, and any storage system that tried to serve both equally well would serve both badly. The divergence you see across cloud storage products isn't a marketing exercise in selling you five things where one would do — it's a direct consequence of the fact that workloads themselves diverged, and no single system optimizes for incompatible access patterns at once.

That's the reframing worth internalizing before anything else: the object/block/file split you find in every provider is an encoding of access pattern, not volume. Once you see it that way, the categories stop being arbitrary product names to memorize and start being predictions you can make. Object storage is built for data you write once and read whole — a video file, a backup, an image. You address it by name, you get the entire thing back, and you don't edit it in place; you replace it. Block storage is built for data you mutate in small pieces at high speed — the disk underneath a database or an operating system, where a program expects to seek to byte offset and overwrite a few kilobytes without rewriting the rest. File storage is built for the case where multiple machines need to read and write the same tree of files through a shared mount, coordinating as if they were all sitting on one computer. Each of these is optimized around a specific pattern of access, and each one is genuinely bad at the others. Trying to run a database on object storage, or trying to share a block volume across a fleet of machines that all want to write, fails in ways that feel mysterious until you remember that you asked a system to do the exact thing it was designed not to.

The reason this matters operationally, and not just conceptually, is that the access pattern a product was built for silently determines its guarantees — and the guarantee people get wrong is consistency. Here is the trap: durability and consistency sound like the same promise and are completely different ones. Durability is a promise about not losing bytes. A system with eleven nines of durability is telling you that once it has acknowledged your write, the probability of that data ever disappearing is vanishingly small. It says nothing whatsoever about whether the next read will reflect what you just wrote. Consistency is that second promise — that a read returns the most recent write — and a storage system can honor the first while quietly breaking the second. It can lose zero bytes across its entire history and still hand you a stale value, because the copy you happened to read from hadn't yet caught up to the copy you wrote to.

This is exactly where object storage burned a generation of engineers who assumed the two guarantees came together. Object stores achieve their durability by keeping many copies across many machines, and for a long time the price of that was eventual consistency: you'd write an object, immediately read it back, and get either the old version or a "not found" — not because anything was lost, but because the read reached a replica that hadn't yet been told about your write. Code written by people who didn't know they were making an assumption about consistency broke, and the breakage was maddening precisely because nothing was ever actually lost. The data was safe. The read was just early. (Most major object stores have since moved to strong read-after-write consistency, which is why this matters less than it used to — but the lesson underneath it is permanent, because the same tradeoff resurfaces anywhere a system replicates data for durability.)

The same lens clarifies the products that sit on top of these primitives. A managed database is block storage plus a great deal of operational machinery the provider runs for you — and the word "managed" is doing sneaky work. It's worth being precise about what it offloads and what it doesn't. Managed means the provider handles the toil you were never good at anyway: patching the database engine, replicating to a standby, failing over when a node dies, taking backups on a schedule. It does not mean the provider handles your schema, your indexes, or your query patterns. A managed database will happily run a catastrophically slow query against a table you forgot to index, replicate that slowness faithfully across every zone, and bill you for the privilege. The line between what "managed" covers and what stays yours is the same shared-responsibility line that runs through every cloud abstraction, and mistaking where it falls is how people end up surprised that "fully managed" didn't save them from a design decision they made themselves.

One more distinction earns its place here because it's the one that turns out to be false comfort in an incident: the difference between keeping a copy and being able to restore to a point in time. "We have backups" and "we can recover to any second before the incident" are not the same claim, and usually only the first is actually true. A backup is a snapshot from some moment — last night, an hour ago — and restoring it puts you back at that moment, losing everything since. Point-in-time recovery is a stronger and more expensive capability that lets you rewind to an arbitrary instant, typically by replaying a continuous log of changes on top of a base snapshot. Most teams discover which one they actually have during the recovery, which is the worst possible time to find out. The gap between those two is measured in exactly how much data you're willing to lose — a question that connects storage directly to the reliability numbers, RPO and RTO, that decide how bad a bad day gets.

So the skill this topic builds is a kind of X-ray vision. When you meet an unfamiliar storage product — from a provider you've never touched, wrapped in a name you've never heard — you don't start by reading the durability marketing. You ask what access pattern it was built to serve: written whole or mutated in place, read by one machine or many, addressed by name or by offset. That single answer predicts the rest. It tells you where the product will be fast and where it will fall over, and it tells you what to go verify about its consistency behavior instead of assuming the pleasant thing. Storage rewards the practitioner who reads it as a statement about how data moves, and punishes the one who reads it as a statement about how much data there is.

## Level 2 candidates

**Object storage semantics** — Covers how object stores achieve durability through replication and what that historically meant for read-after-write behavior. Worth going deeper because the eventual-consistency era left behind a set of defensive patterns still worth understanding, and because the same durability-versus-consistency tradeoff recurs in any replicated system you'll meet.

**Block storage and IOPS** — Covers the throughput and operations-per-second ceilings that govern how fast a block volume can actually serve reads and writes. Worth going deeper because it explains the genuinely counterintuitive fact that a bigger disk can perform worse, and because IOPS limits are a common invisible cause of database slowness that looks like an application problem.

**File storage and shared mounts** — Covers concurrent-write semantics when multiple machines read and write the same filesystem tree. Worth going deeper because shared-mount coordination is the quiet source of some of the hardest bugs in distributed systems, and the failure modes are subtle enough that they rarely appear until real concurrency does.

**Managed databases** — Covers precisely what the "managed" label offloads (patching, replication, failover, scheduled backups) versus what stays your responsibility (schema, indexing, query performance). Worth going deeper because the boundary is routinely misjudged, and because it's a concrete instance of the shared-responsibility line that runs through the entire course.

**Backup, snapshot, and point-in-time recovery** — Covers the mechanical difference between restoring a snapshot from a fixed moment and replaying a change log to rewind to an arbitrary instant. Worth going deeper because the gap between these two capabilities is exactly the data you'd lose in an incident, and because it connects directly to RPO and RTO as testable commitments rather than vague reassurances.
