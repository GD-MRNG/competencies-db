# L1-02 · The Shell

When you type `ls` and hit enter, something has to read those two letters, decide they name a program, find that program, run it, and show you what it produced. That something is not the terminal window — the terminal window is just drawing text. It is not the operating system — the OS doesn't care what you typed. It is a specific program, sitting in between, whose entire job is to be the interpreter for your keystrokes. That program is the shell, and almost everything you have ever called "knowing the terminal" is actually knowing one particular shell's particular dialect.

This is the layer where most of what feels like inconsistency in command-line work actually lives, and recognizing that is the first real payoff of separating it out. When a command works on your colleague's machine and not yours, when a tutorial's example fails in a way the tutorial didn't warn about, when something behaves one way in a script and another way at the prompt — the explanation is overwhelmingly that a different shell, or the same shell in a different mode, is doing the interpreting. The terminal emulator and the OS underneath are remarkably stable across these situations. The shell is not.

The mental model worth installing is this: a shell is an interpreter for a programming language whose primary verb is "run this program." Every time you press enter, the shell parses what you typed as a small program in its language, evaluates it (which usually means asking the OS to launch one or more processes), prints whatever those processes wrote, and loops back to read the next line. The interactive prompt and a shell script are not two different things — they are the same interpreter, one reading from your keyboard and the other reading from a file. This is why shell scripts have variables, loops, conditionals, and functions: you are not using a "command line" that has been awkwardly extended into a scripting language, you are using a scripting language whose REPL happens to be where you live all day.

Once you see the shell as an interpreter, the proliferation of shells stops being noise and starts being legible as a history. Bash, zsh, and fish are siblings in the Unix lineage, each adding features over its predecessors — better completion, better history, better prompts, friendlier defaults — while staying close enough in syntax that a script written for one mostly works in another. They share the deep assumption of the Unix tradition: everything flowing between programs is text, and your job as a shell user is to compose small text-transforming programs into pipelines. PowerShell sits in the same architectural slot — read input, interpret, run things, print results — but was designed in a different decade with a different bet. Its pipelines pass structured objects, not bytes. Where a Unix shell hands you a chunk of text and expects you to slice it with tools like `grep`, `awk`, and `cut`, PowerShell hands you an object and expects you to access its properties by name.

This difference is the deepest cross-platform seam in everyday terminal work, and treating it as a stylistic preference will mislead you. A command that pipes `ls` into `grep` in bash is doing text processing on text. The visually similar PowerShell pipeline is doing object filtering on objects that happen to render as text when printed. Translating commands between the two by syntactic substitution will produce things that look right and behave subtly wrong. The two shells are not dialects of one language; they are two different languages that happen to share an architectural role and a rectangular window.

The other place the shell-as-distinct-layer model pays off immediately is configuration. Files like `.bashrc`, `.zshrc`, and PowerShell's profile scripts are not "terminal settings" — they are code that the shell runs at specific moments in its own lifecycle (when it starts as a login shell, when it starts as an interactive shell, when a new tab opens). This is why a command that worked in one terminal tab fails in another, or works after a reboot but not before, or works at the prompt but not in a script: different shell invocations run different subsets of those configuration files, so they end up with different aliases, functions, and environment in scope. None of this is the terminal's fault and none of it is the OS's fault. It is the shell, running its configured startup code, in a context whose rules you have not yet read.

The practical skill this topic builds is the habit of asking, when something behaves unexpectedly on the command line, which shell is interpreting this and in what mode. That question is almost free to ask once the shell is a distinct thing in your head, and it cuts through a surprising fraction of confusion. "Why does this work in bash but not PowerShell" is no longer a puzzle; it is the expected outcome of feeding the same input to two different interpreters. "Why does my script behave differently from the same commands at the prompt" stops being mysterious once you notice the script ran in a non-interactive shell that didn't source your interactive config. The commands you have been memorizing are not facts about computers. They are syntax in a specific language, spoken by a specific program, and once you can name that program, you can finally start learning the language instead of the lines.

## Level 2 candidates

**REPL loop (read–eval–print)** — Covers the shell's actual job in one sentence: read a line, figure out what program(s) it names, run them, print the result, repeat. Worth deeper attention because nearly every other shell concept — job control, redirection, exit codes, prompt behavior — attaches to a specific step of this loop, and seeing the loop explicitly makes those concepts derivable rather than separately memorized.

**Built-ins vs external commands** — Covers why some commands like `cd`, `export`, and `alias` must be implemented inside the shell itself while others like `ls` and `grep` are separate programs the shell launches. Worth going deeper because the distinction explains a genuinely confusing class of behavior (a separate process literally cannot change *your* shell's working directory or environment) and clarifies why `which cd` does something different from `which ls`.

**Shell scripting as a real programming language** — Covers the realization that `.sh` files use the same interpreter as your interactive prompt, with variables, loops, conditionals, and functions. Worth depth because most people treat shell scripts as "lists of commands" and consequently write fragile ones; treating the shell as a programming language with a type system (basically: strings) changes how you write and debug them.

**PowerShell's object pipeline vs Unix's text pipeline** — Covers the deepest philosophical divergence: PowerShell pipes structured .NET objects between commands while Unix shells pipe raw bytes. Worth deep treatment because it is the single concept that most reliably prevents bad cross-platform translation, and because understanding *why* each design made sense in its era is more durable than memorizing the surface differences.

**Shell configuration files (`.bashrc`, `.zshrc`, profile scripts)** — Covers what runs when, across login shells, interactive shells, and non-interactive script invocations. Worth depth because the rules are genuinely non-obvious, differ across shells, and are the direct cause of a recurring category of "works here but not there" bug that no amount of command-memorization will resolve.

**Why there are so many shells** — Covers the lineage from sh through csh, bash, zsh, and fish as a history of incremental feature competition. Worth a brief deep dive because seeing the lineage makes the choice of which shell to use an informed decision rather than a coin flip, and explains why bash remains the lowest-common-denominator target for portable scripts despite zsh and fish being nicer to live in.

#### L1-02 · The Shell
The shell — bash, zsh, fish, PowerShell — is the actual program that reads what you type, interprets it as a command, and asks the OS to do something. This is the layer most "command memorization" actually lives in, and it's also where most of the *inconsistency* you've felt comes from: bash, zsh, and PowerShell are genuinely different programs with different syntax, different scripting languages, and different philosophies (Unix shells assume "everything is text"; PowerShell, designed decades later, assumes "everything is a structured object"), even though they're all sitting in the same architectural slot. Once the shell is its own distinct layer in your head, "why does this work in bash but not PowerShell" stops being a mystery and becomes an expected consequence of using two different programs that happen to look similar.
