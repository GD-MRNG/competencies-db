# L1-09 · Environment and Configuration

The single most frustrating class of bug in a developer's life isn't a logic error — it's the bug that disappears when you look at it. The script that runs from your terminal but fails under cron. The deploy that works on your laptop and breaks on your colleague's. The command that worked yesterday, before you opened a new tab. These aren't flaky systems and they aren't bad luck; they're almost always the same underlying phenomenon, which is that two processes you thought were "the same" were in fact running with different invisible state attached to them. That invisible state has a name — the environment — and once you can see it, this entire category of bug stops being mysterious and starts being diagnosable.

The mental model worth installing is this: every process on your machine carries around a small private dictionary of string variables, inherited from its parent at the moment it was created. That dictionary is the environment. It contains things like `PATH` (where to look for executables), `HOME` (where your files live), `LANG` (what language to format messages in), and whatever else has been set along the way. When the shell launches a program, it hands that program a copy of its current environment. The program can read it, modify its own copy, and pass that modified copy on to any children it spawns — but it cannot reach back up and change its parent's environment. Inheritance flows strictly downward, and it happens exactly once, at the instant of process creation.

This one-way, snapshot-at-birth nature is the source of almost every confusing symptom in the category. If you set a variable in one terminal tab, the tab next to it doesn't see it, because that other tab is a sibling process whose environment was copied from a common ancestor before you made the change. If a long-running shell session has a stale `PATH` and you edit your config file, the running shell still has the old value — you have to start a new shell (or explicitly re-source the file) for the change to take effect. If a child process changes its own `PATH` and exits, your shell's `PATH` is unaffected, because the child was only ever modifying its own copy. None of this is a quirk; it's the direct consequence of how processes are created.

The next thing to internalize is the distinction between a shell variable and an environment variable, which sounds pedantic until it bites you. When you type `FOO=bar` at a bash prompt, you've set a shell variable — visible inside this shell, invisible to anything it launches. When you type `export FOO=bar`, you've marked it for inheritance, and now every child process the shell spawns will see it. This is why `export` exists as a separate verb: it's the toggle that decides whether a variable crosses the process boundary or stays local to the shell that defined it. Forget to export, and your carefully-set variable will be silently absent from the program that needs it.

Layered on top of that is the configuration-file system, which is what makes the environment feel both convenient and treacherous. Files like `.bashrc`, `.bash_profile`, `.zshrc`, and `.profile` exist to populate the environment automatically when a shell starts — but they don't all run in all contexts. Some run only for login shells (the shell you get when you SSH in or log in at a console). Some run only for interactive shells (the kind with a prompt). Some run only for non-login interactive shells (a new terminal tab on most systems). The result is that the environment you experience depends not just on the machine but on how the shell on that machine was started, and "how it was started" is something you almost never think about until it goes wrong.

This is the mechanism behind the famous "works in my terminal, not in cron" puzzle. When cron runs your script, it launches a shell that is neither a login shell nor interactive, so none of your usual config files load. The carefully curated `PATH` that lets you type `python` or `node` and have it just work? Cron's shell has never heard of it. The same script, run by you directly, succeeds; run by cron, it fails to find half its tools — not because cron is broken, but because cron's shell was born into a much sparser environment than yours, and the configuration files that would have enriched it never executed. The same principle explains why a script run via your IDE's "Run" button can behave differently from the same script run from a terminal: the IDE spawned its shell differently, with a different config-file lineage.

The practical skill this topic builds is the habit of asking, whenever something behaves inconsistently across what looks like "the same machine," what the environment actually was at the moment the failing process started. Run `env` (or `printenv`, or `Get-ChildItem Env:` in PowerShell) inside the failing context — even if that means temporarily having the failing script dump its environment to a log — and compare it to the working one. You will almost always find the difference there: a missing variable, a `PATH` without the directory you needed, a locale set to something the program can't handle. Environment problems feel like ghosts because the environment is invisible by default; the entire fix is to make it visible.

The deeper move, once you have this model, is to start treating environment as code. Version-control your dotfiles. Be explicit in scripts about what they require — set `PATH` deliberately at the top of a cron script rather than hoping it inherits something useful. When you onboard a new machine or write a deployment, write down the environment it needs rather than reproducing it by hand and hoping you got it right. Environments drift; written ones drift less.

**Variable scope and inheritance** — Covers the precise mechanics of how environment copies flow from parent to child at process creation, and the contrast with shell variables that never cross that boundary. Worth a deeper look because the `export` distinction and the downward-only flow are subtle enough that most engineers carry a fuzzy version of them for years, and the fuzz is exactly what produces "why doesn't my child process see this" bugs.

**Login shells vs interactive non-login shells** — Covers the matrix of which config files (`.bash_profile`, `.bashrc`, `.zshenv`, `.zshrc`, `.profile`) run in which startup contexts, and why. Worth going deeper because this is the direct mechanical cause of the "works in my terminal, not in cron / not in my IDE / not over SSH" family of bugs, and the rules are arbitrary-looking enough that you genuinely have to learn them once rather than derive them.

**`$PATH` ordering and shadowing** — Covers how the shell resolves a bare command name by walking `PATH` left to right and taking the first hit, and the consequences when two directories contain different versions of the same tool. Worth deepening because `PATH` shadowing is the cause of an outsized share of "wrong Python," "wrong git," and "why is this old binary running" mysteries, and the fix requires understanding both order and how to inspect it (`which`, `type -a`, `command -v`).

**Cross-platform environment differences** — Covers how environment variables, separators (`:` vs `;`), and configuration-file conventions differ between Unix-like systems and Windows. Worth a Level 2 because scripts with hardcoded environment assumptions are one of the most common things that break the instant they cross platforms, and the differences are mechanical and learnable rather than judgement calls.

**Dotfiles as portable configuration** — Covers the practice of version-controlling shell and tool configuration so that a new machine can be brought to a known environment state quickly and reproducibly. Worth deepening because it's the practical bridge from understanding environments to controlling them, and the tooling patterns (symlink farms, `stow`, chezmoi, bare-repo tricks) are worth learning once rather than reinventing per machine.

## Original Content

#### L1-09 · Environment and Configuration
"Why does this work on my machine but not yours" and "why did this work yesterday but not today" overwhelmingly trace back to environment state — variables, `$PATH` entries, shell configuration files — that's invisible unless you go looking for it. This topic is really the practical synthesis of L1-02 (shell) and L1-04 (processes): environment variables are inherited at process-creation time, set by configuration files that run at specific, orderable moments, which is why two terminal tabs, a script run directly, and the same script run via cron can all see different environments despite "the same machine."
