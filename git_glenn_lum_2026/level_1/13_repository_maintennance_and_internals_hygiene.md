# L1-13 · Repository Maintenance and Internals Hygiene

Most of the time, you do not think about Git's internals at all — you commit, you push, you move on, and the object database quietly absorbs whatever you throw at it. Then one day a clone takes twenty minutes, or `.git` is somehow eight gigabytes on a project whose working tree is two hundred megabytes, or a command fails with a message about a corrupted object and you realize you have no idea what state the storage layer is even in. This topic is what you reach for in those moments. It is less about daily workflow and more about understanding the housekeeping Git is doing behind your back — and what happens when that housekeeping has been skipped, interrupted, or has work to do that you never triggered.

The starting point is to remember what the object database actually looks like in its naive form. Every blob, tree, and commit is written as a separate file under `.git/objects/`, named by its SHA. This is conceptually beautiful and operationally fine for a small repository, but it does not scale. A project with five years of history can easily produce hundreds of thousands of objects, and a filesystem full of hundreds of thousands of small files is slow to traverse, slow to transfer over the network, and wasteful of disk because each object is compressed in isolation rather than against its neighbors. The loose-object model is the simple version of Git's storage; it is not the version a healthy long-lived repo actually runs on.

The fix is packfiles. A packfile is a single file containing many objects, stored together with delta compression — instead of compressing each version of a large file independently, Git stores one full copy and expresses the others as diffs against it. This is dramatically more space-efficient and dramatically faster to transfer, which is why `git fetch` and `git push` ship packfiles rather than streams of loose objects. Garbage collection, invoked as `git gc` and run automatically by Git at various thresholds, is the operation that consolidates loose objects into packfiles, drops objects no longer reachable from any ref or the reflog, and generally compacts the database. When someone tells you their `.git` directory shrank by ninety percent overnight, gc is almost always what happened.

Reachability is the concept that determines what gc keeps and what it throws away. An object is reachable if you can get to it by following pointers from some ref (a branch, a tag, HEAD) or from the reflog. Anything else is dangling — a real, valid object sitting in the database with nothing referencing it. This is exactly the state a commit ends up in after, say, a hard reset that moves a branch backward: the commits the branch used to point to are still in the database, they are just no longer reachable from any branch. The reflog keeps them findable for around ninety days by default, which is why "lost" commits are almost never actually lost during that window. Pruning, the step of gc that deletes unreachable objects, is what finally makes them gone for real. Understanding this is what lets you reason about recovery: a commit is recoverable until something has actively pruned it, and the reflog is the index of what to look for.

Then there are the integrity tools, of which `git fsck` is the one worth knowing by name. It walks the object database and verifies that every object's content matches its hash, every pointer points to something that exists, and the graph is structurally consistent. You will rarely run it, but when you suspect actual corruption — a disk error, a killed gc, a half-finished clone over a flaky network — fsck is how you tell whether your repo is genuinely broken or merely behaving strangely for some other reason. It is the difference between "this is a Git problem I can think about" and "this is a storage problem I need to recover from."

A few smaller pieces of hygiene live in this topic because they share the same flavor of "Git is doing something underneath that you can't see until you know to look." `.gitignore` is the canonical example: it only affects untracked files, so adding a pattern for a file that is already tracked does nothing, and the resulting confusion ("I added it to .gitignore, why is it still showing up?") is really a question about what state the index is in, not what the ignore file says. Hooks are another: the `.git/hooks/` directory contains executable scripts that run at specific points in Git's lifecycle (pre-commit, pre-push, post-merge), and they are how teams attach linting, validation, or policy enforcement to Git operations — but they live inside `.git/`, which means they are not versioned and not shared by cloning, which is why hook-distribution is a recurring minor headache that tools like Husky exist to paper over.

The practical posture this topic builds is not "run gc regularly" — modern Git does that for you. It is the ability to look at a misbehaving repository and form a hypothesis about which layer is misbehaving. Is it slow because there are too many loose objects? Is it huge because gc has not run, or because a large binary is genuinely in the history forever? Is something missing because it was pruned, or because it was never committed? Is a file being ignored because of `.gitignore`, or being tracked despite it? Once you can see the object database as a thing with its own state — separate from your working directory, separate from your refs — these questions become diagnosable instead of mystifying. That is the entire payoff: not a daily skill, but a debugging stance for the moments when Git stops feeling like a tool and starts feeling like a black box.

**Packfiles and `git gc`** — Covers how loose objects get consolidated into delta-compressed packfiles and what triggers automatic vs manual garbage collection. Worth deeper exploration because the mechanics of delta compression and pack indexes are what make Git's storage genuinely efficient at scale, and understanding them demystifies dramatic size changes after gc.

**`git fsck`** — Covers how Git verifies the integrity of its own object database, what kinds of corruption it detects, and what its output actually means. Worth a deeper look because it is the tool you reach for when you suspect real corruption rather than mere confusion, and its output is opaque until you have walked through it once on a healthy repo.

**Dangling commits and pruning** — Covers what "dangling" means precisely (an object with no ref reaching it), how the reflog keeps such objects findable for a recovery window, and what pruning does at the end of that window. Worth deeper exploration because this is the mechanism underneath nearly all of Git's "lost commit" recovery stories, and knowing exactly when an object becomes truly unrecoverable is the difference between calm and panic during an incident.

**`.gitignore` semantics and the already-tracked file problem** — Covers why ignore patterns only apply to untracked files and what to do when a file has already entered the index. Worth deeper exploration because the failure mode is universal — every engineer hits it eventually — and the fix requires understanding the index, not just the ignore file.

**Git hooks** — Covers the lifecycle extension points Git exposes (pre-commit, pre-push, post-merge, and friends) and the constraints around them, particularly that they are not versioned with the repo. Worth deeper exploration because hooks are how teams actually enforce policy at the Git layer, and the distribution problem (how to share hooks across a team) is a recurring practical question with several real answers.
