# L1-04 · Commits as a Directed Acyclic Graph

The reason Git history feels confusing when you come from any other tool — or from no version control at all — is that you're almost certainly picturing it as a timeline. A list. A sequence of saves, like the undo history in a text editor, with maybe some branches drawn off to the side as a visual convenience. That picture is wrong, and most of the operations that mystify people (rebase, cherry-pick, bisect, "why is my log out of order") are mystifying specifically because you're trying to project a graph onto a line and the projection keeps losing information.

The actual structure is simpler than the timeline picture, once you see it. A commit in Git is an object that points backwards at its parent commit — that's it, that's the whole link. A first commit has no parent. A normal commit has one parent. A merge commit has two (occasionally more). Because every commit only ever points backwards, and because commit identities are content-addressed hashes that can't be retroactively edited, you can never construct a cycle: there is no way for commit A to be its own ancestor. That property is what makes the structure a DAG — a directed acyclic graph — rather than just "a graph." Directed, because the parent pointers have a direction. Acyclic, because the design forbids loops.

Once you internalize this, "history" stops being a sequence and becomes a shape. A branch isn't a parallel timeline; it's a name pinned to one node in the graph, and what we casually call "the history of that branch" is really the set of all commits you can reach by walking parent pointers backwards from that node. Two branches that share a common ancestor look like a fork in the graph. A merge looks like a diamond: two parallel paths that diverge from one node and reconverge at another node which points back at both. Linear history — the kind you'd see in CVS or SVN — is just the special, degenerate case where every commit has exactly one parent and no branches ever reconverge. Git treats divergence and reconvergence as first-class structural facts, not as edge cases bolted onto a list.

This is the conceptual leap that makes Git's whole feature set make sense, because it turns out that most of the "advanced" commands aren't really separate features at all. They're each a different operation on this same graph. Rebasing is "walk a chain of commits, take each one's diff, and replay it onto a different starting node" — you are literally lifting a path off the graph and reattaching it somewhere else. Cherry-picking is the single-node version of that. Bisecting is binary search over the graph: given a known-good ancestor and a known-bad descendant, Git keeps picking the midpoint of the reachable set until it finds the commit that introduced the regression. `git log A..B` — one of the most useful incantations you'll ever learn — is a graph query: "give me every commit reachable from B but not from A." That query is what every pull request diff view is built on, and once you see it as a graph operation, the answer to "what's actually in this PR" becomes mechanical rather than mysterious.

A few specific confusions dissolve immediately under the graph view. Why does `git log` sometimes show commits in an order that looks wrong chronologically? Because `git log` walks the graph, not the clock, and a merge brings in a side branch whose commits may have been authored at any time. Why does `--first-parent` exist? Because at a merge commit, parent number one is conventionally the branch you merged into and parent number two is the branch you merged from — so following only first parents gives you the "main line" view and hides the side-branch detail. Why does merging sometimes produce a merge commit and sometimes silently not? Because if the target branch's tip is already an ancestor of the source branch's tip — a straight line in the graph — there's no diamond to create, and Git just slides the branch pointer forward (a fast-forward). The `--no-ff` flag is how you force a diamond even when the geometry doesn't require one, usually because your team wants merge commits as explicit markers of integration points.

The other thing the graph view buys you is a more honest relationship with tools like `git log --graph`. The ASCII art it draws isn't decoration; it's a faithful rendering of the actual data structure on disk. The vertical lines are branches of the DAG. The asterisks are commits. The forks and joins are exactly where parent pointers diverge and reconverge. If you can't read that output, it's not because the visualization is bad — it's because you don't yet have a mental model for what it's visualizing. Once you do, it becomes one of the most information-dense diagnostic tools in the entire system, and the moment you reach for it before a tricky merge or rebase is the moment you stop operating on Git by superstition.

The practical skill this topic builds is the ability to predict the shape of your history before you run a command, and to read the shape that exists after. Every other graph-touching topic — merging, rebasing, cherry-picking, bisecting, ancestry queries — is downstream of being able to do that. If you find yourself confused by what a Git command did, the first move is almost always to draw the graph, or ask Git to draw it for you. The command surface is leaky and inconsistent; the graph underneath is not.

Worth a deeper look because the first-parent convention is what tools like `git log --first-parent` exploit to give you a clean "main line" view of an otherwise noisy history, and getting the convention backwards in a workflow corrupts that view permanently.

**Ancestry and reachability (`git log A..B`)** — Covers the graph-query syntax for "what's reachable from B but not from A," along with related operators like `A...B` (symmetric difference) and `^A`. Worth going deeper because nearly every code review tool, PR diff, and "what's in this release" question is built on these reachability queries, and being fluent in them lets you ask precise questions instead of eyeballing log output.

**Common ancestors (merge base)** — Covers the algorithm Git runs before any merge or rebase to find the most recent commit reachable from both branch tips, and the cases where there isn't a unique answer. Worth descending into because an unexpected merge base is the silent cause of baffling merge diffs and surprising rebase conflicts — if you can compute the merge base in your head, you can predict the conflict surface before you start.

**`git bisect`** — Covers using Git's built-in binary search over the DAG to localize a regression to a specific commit, including the marking of good and bad endpoints and the handling of merge commits during the search. Worth a deep dive because it's the clearest demonstration that history-as-graph isn't just a metaphor — it's a searchable data structure — and it turns "which of these 200 commits broke this" from a guessing game into roughly eight checkouts.

**Fast-forward vs non-fast-forward merges** — Covers the geometric condition under which Git can integrate one branch into another by simply moving the branch pointer forward, versus when it must construct an actual merge commit. Worth deeper exploration because the choice between fast-forward and `--no-ff` is one of the most consequential team-policy decisions about what your history will look like a year from now, and it's almost always made by accident rather than design.

#### L1-04 · Commits as a Directed Acyclic Graph
Once you know a commit just points to its parent(s), "history" stops being a timeline and becomes a graph — specifically a DAG, since a commit can have multiple parents (merges) but you can never travel forward in time into a cycle. This is the conceptual leap that explains why Git branching is fundamentally different from, and more powerful than, the linear history models of older systems: divergence and reconvergence are first-class, not edge cases bolted on. Most "advanced" Git operations — rebasing, cherry-picking, bisecting — are really just different ways of walking, rewriting, or searching this graph. Seeing history this way is also what makes tools like `git log --graph` legible instead of decorative ASCII art.
